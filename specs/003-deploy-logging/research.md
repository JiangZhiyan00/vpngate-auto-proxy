# 研究结论：简化部署准备与运行日志

日期：2026-10-16，上海时区。依据 [功能规格](spec.md) 及当前仓库，只做设计，不视为实现或运行验收。

## 一、宿主入口与分发

**决定**：提供独立、版本化、纯 Python 标准库的部署安装器，定位与现有 `scripts/install-vap.py` 一致，不新增第二套产品命令，不安装原生代理。生成的单文件安装器内嵌所选版本的生产策略及其摘要，可脱离源码目录执行。发布说明生成一条明确版本的首次准备命令，在管理员私有临时目录下载、核对预期 SHA256 后执行；禁止未校验即执行下载内容。

**理由**：现有 Dockerfile 的 `RUSTFLAGS=-C target-feature=-crt-static` 及 Alpine OpenSSL 动态依赖说明镜像程序不是可直接运行于 Debian／Ubuntu 的宿主程序。仅准备策略无需新增完整宿主二进制分发。安装器是部署材料，不伪装为 `vap`、不创建别名；本功能不新增公开产品子命令，后续若扩展产品命令仍须用 `vap`。

**考虑过的替代**：直接复制镜像程序到宿主不可保证运行；特权初始化容器扩大宿主管理权限；另建宿主原生代理发布增加系统依赖和来源核验成本；下载整个源码再执行三条命令不满足部署简化目标。

**信任边界**：固定官方 GitHub Release 的严格版本地址和公开摘要，拒绝 `main`、`latest`、用户任意 URL 与未知安装路径。SHA256 验证完整性和版本绑定，不能宣称它提供独立签名认证。引导命令自身是用户从可信发布说明取得的信任起点。安装器执行后不再联网，策略内嵌且只允许一个明确策略名。

**分发衔接**：追加小型安装器、宿主材料清单及一条命令说明到同版本公开附件和源码白名单；保留原完整来源归档、先验收后公开附件、再推送版本及 latest 的顺序。只增加本功能必要部署材料，不改变触发规则、镜像架构或重写旧发布。

## 二、加载、持久化与事务

**决定**：首个支持矩阵为 Debian 12、Ubuntu 24.04，Linux x86_64、有根本机 Docker、systemd 和启用的 AppArmor；要求宿主 Python 3.10 以上、必要系统命令、标准策略包含文件及 `/dev/net/tun`。拒绝容器内部、远端 Docker 上下文、无根引擎及未知支持环境；只报告依赖缺失，不安装系统软件。

**理由**：自定义 AppArmor 策略必须预先加载到宿主内核；单纯解析策略或检查 Docker SecurityOptions 不足以证明可用。[Docker 官方文档](https://docs.docker.com/engine/security/apparmor/)规定了预加载与容器策略选择关系。

**决定**：固定策略文件 `/etc/apparmor.d/vpngate-auto-proxy`，登记与恢复材料 `/var/lib/vap-host`，项目锁 `/run/lock/vap-host-init.lock`；root 管理、受保护路径、拒绝链接和危险权限。先无副作用解析并确认唯一策略名称，再按需加载，最后核对内核列表中精确名称和 enforce 模式。显式跳过旧缓存读取，避免文件更新却加载陈旧缓存。只调用项目单个策略，不 reload 全部 AppArmor 服务。

**理由**：`apparmor_parser` 的 `--names`、`--skip-kernel-load`、`--skip-read-cache`、`--replace` 含义见 [Debian 12 官方手册](https://manpages.debian.org/bookworm/apparmor/apparmor_parser.8.en.html)。解析及名称检查只能作为准备步骤，不能替代真实加载检查。

**决定**：通过系统现有启动加载链持久加载，检查策略未在 disable／force-complain 中、AppArmor 单元已加载且持久启用、未屏蔽，并核对支持发行版的启动依赖；不自动启用、重启或重载系统服务。首次可报告“当前加载和持久配置检查通过”，只有真实宿主重启证据才能标记“重启验证通过”。

**依据**：[Debian AppArmor 启动单元](https://sources.debian.org/src/apparmor/3.0.8-3/debian/apparmor.service)的 sysinit 启动关系，以及 [Ubuntu 官方部署说明](https://documentation.ubuntu.com/server/how-to/security/apparmor/index.html)的策略路径和启停方式。实现需按实际目标发行版检查，不能仅用一个 is-active 布尔量证明重启行为。

**事务决定**：先获取项目独占锁、核对所有路径与现态、保存只属于本项目的旧材料及事务意图，再提交策略、按需加载、复核内核与磁盘，最后写完成登记。加载或复核失败时恢复旧文件和登记；恢复内核必须依据事务确认的旧状态，不能卸载未知或被使用的策略。恢复不确定时返回专门失败状态及恢复路径，不报告成功。异常中断留下的事务必须先恢复或明确拒绝后续写入。

**重复与更新**：同版本同摘要且 enforce 正确时不 reload；尚未加载时才加载。没有登记的现有同字节官方策略只能经显式接管流程处理；未知字节、未知内核同名策略或登记不一致均拒绝。不同版本默认拒绝，显式更新绑定登记的旧版本和摘要。任何需要替换内核策略的操作，先核对所有受该策略约束的宿主进程已退出，无法完整确认即拒绝；安装器不停止代理或其他服务。

## 三、日志实现与兼容性

**决定**：保留逐行 JSON 和标准错误的外部日志契约，新增轻量 `src/logging.rs`、`LogLevel` 和显式 `LogPolicy`，使用已存在的 serde、chrono、tokio，不新增依赖或整体迁移 tracing 格式。`Event` 增加 `level`，既有字段保留，`StatusSnapshot` 和公开状态返回不改变。

**理由**：`src/service.rs::emit` 和 `emit_summary` 当前直接无条件输出；只设置 RUST_LOG 不会改变这些输出。明确等级枚举和序列化前过滤可保持原事件结构及现有解析成本。配置整体在 Linux Bootstrap 中传递，不能依赖 env_clear 后的环境继承。

**过滤边界**：只包围构造和输出事件，不包围调度、保存状态、健康检查或清理。周期摘要使用独立单调 Instant，下一次为当前时间加配置间隔，延迟后不集中补发；不改 100 毫秒主循环、每秒结构检查或出口健康频率。

**外部输出决定**：原始隧道输出不得直接透传到公开日志；既有管理结果提供安全失败阶段，详细输出若采集则持续排空、有字节上限、仅生成白名单事件。不得只读一段后停止排空管道导致子进程阻塞，不能把普通候选失败全部升级为警告。

## 四、多进程租约与日志通道

**决定**：Linux 沿可信 Bootstrap／启动参数显式传递策略；已有安全诊断继续在持有配置的监督方输出。苹果的 stderr 租约保持原状；若控制进程需输出启动摘要或协调事件，使用单独受控、只承载安全事件的诊断通道，由父方重建并输出，禁止把租约描述符换成 inherit、null 或日志管道。

**理由**：`src/platform/process.rs::Receipt::child_stderr` 经 `src/platform/lease.rs::ConsumerLease::child_stdio` 让消费者继承锁句柄。改动这个描述符会改变崩溃隔离及资源退休。苹果真正协调循环位于子控制进程，不能仅修改 service::emit 而忽略它的输出目的地。

**诊断通道约束**：固定版本、每帧至多 4096 字节，总 64 帧含 1 帧首次监听保留槽位和 63 帧普通事件；完整摘要由父方已有配置重建。发送非阻塞，debug 丢弃，普通 info／warn／error 按明确等级淘汰或合并，四个固定饱和计数器报告交付损失，不能因拥塞阻止控制失联退休。关键退出阶段及原因独立保存到可信失败结果，若原收据只有回收布尔量须补充安全原因结果；最终写入也不能无限阻塞。结束排空至多 1 秒且计入原十五秒总预算。未知帧拒绝，描述符仅传给预定消费者，诊断方不得额外持有 utun 或管理控制句柄。现有公开控制命令、就绪查询和租约归属不因日志变化扩大；详见日志契约的逐等级规则。

**考虑过的替代**：整体接管 stderr 会破坏租约；把未经限制的日志复用到关键控制流可能造成控制阻塞；直接转发子进程原始文字无法保证脱敏。

## 五、真实启动与安全摘要

**决定**：把 `socks::run_gateway` 的真实绑定与服务循环分开，监听对象只绑定一次并由服务循环持续持有；绑定成功后输出一次摘要，再进入候选调度与服务循环。两平台共用这一语义。摘要为信息事件，warn／error 下不输出。

**理由**：`src/service.rs` 的预先 bind 后 drop 只是预检；实际绑定在 `src/socks.rs`。苹果内部 Ready 握手目前也早于实际监听，不能直接作为成功证据。失败时走原有取消和清理流程，不发成功摘要。

**白名单决定**：独立 StartupSummary 只包含实例、实际地址与端口、协议、监听范围、地区、时区、连接上限、日志设置、数据及运行目录、认证布尔值和当时 ready。容器启动模式通过可信入口传递，仅用于显示，不从任意用户环境推断宿主端口。原生默认显示本进程范围，容器显示内部范围；不请求 Docker socket。

**安全决定**：不序列化整个 AppConfig，不打印用户名、凭据内容、源 URL、检测 URL、完整错误链或原始外部程序输出；配置错误通过字段名和固定安全原因定位。启动摘要不包含认证路径或可由敏感正文拼出的说明。

## 六、验证与研究关闭

- 宿主文件事务可在隔离目录模拟；真实内核 enforce、其他策略不变和正常重启持久性必须在两种目标宿主验证，普通容器中的 root 文件测试不能替代。
- 默认等级将隐藏现有调试事件；依赖这些事件的行为测试明确选 debug。`validate_docker.py` 的缓存与候选否定判断改用状态证据和专门调试场景，不能把日志缺失当作没有启动候选。
- 十分钟安静场景、四等级、1／60／300 秒摘要频率、端口占用、敏感标记及故障阻断／恢复／退出回收组成本功能验收，不无依据要求重跑网络设计未改变的全部长测。
- 苹果通道变更需执行租约持有、控制失联退休、输出拥塞及描述符回收回归；平台专用测试不在 Linux 冒跑，苹果完整生产验收仍独立标记。

所有影响设计的未知项已形成上述明确决策；剩余内容是实现和目标环境验收，不作为已通过结果。
