# 版本标签与镜像发布契约

对应 US7、需-021、成-013；本契约于 2026-10-15 实现后补审。操作说明见[发布指南](../../../docs/dockerhub-release.md)。

## 输入与触发

| 输入 | 契约 |
| --- | --- |
| Git 标签 | 严格 `v主.次.修订`，每段为零或无前导零的非负整数，例如 `v1.0.0`；不接受预发布及构建后缀 |
| GitHub 仓库 | 公开；维护者允许发布任务写入版本附件 |
| `DOCKERHUB_USERNAME` | GitHub 密钥，Docker Hub 登录账号，不写入源码或日志 |
| `DOCKERHUB_TOKEN` | GitHub 密钥，对目标仓库有写权限的访问令牌，不与代理访问凭据混用 |
| `DOCKERHUB_IMAGE` | GitHub 变量，Docker Hub 小写命名空间及仓库，例如 `example/vpngate-auto-proxy`；不包含标签、摘要、域名或端口；命名空间不能含点或为 `localhost`，仓库名可含点；构建前拒绝其他注册表解析 |
| 目标平台 | Linux amd64，即 x86_64；其他架构和原生二进制不在此发布契约内 |

普通分支提交不触发镜像发布。标签触发模式可接收部分最终不合格的标签；进入构建及推送前必须由严格校验拒绝它们，不能将触发模式视为完整版本校验。每次正式发布推送与合法 Git 标签一致的镜像标签，并更新 `latest`，两者指向同一镜像；补发旧版本也按本规则更新 `latest`。

## 顺序与拒绝行为

1. 校验标签、仓库公开性、镜像名及密钥是否配置；不打印密钥值。
2. 运行格式、静态检查及普通测试，加载产品及夹具专用安全策略。
3. 构建固定架构产物，采集锁定依赖、系统包来源、完整配方及原始声明；核验最终镜像身份与分发材料。
4. 对最终镜像完成强制 AppArmor 下的受控短试；检查构建期间程序输入未变化，再冻结完整来源和摘要。
5. 向同名 GitHub 版本发布上传公开完整源码材料、摘要和验收记录。
6. 登录 Docker Hub，先推送已经核验镜像的版本标签，成功后为同一镜像添加并推送 `latest`；推送阶段不重新构建。版本标签推送失败不更新 `latest`，仅最新标签推送失败时保留已发布版本并报告失败。

步骤 1—5 任一失败不得执行步骤 6。附件已公开而后续失败时允许保留附件；附件存在不表示镜像已发布。脚本只生成本地材料时 `publication_performed` 不得被解释为远端完成；本地准备记录与远端核验记录分开。

## 输出与核对

| 输出 | 核对依据 |
| --- | --- |
| `命名空间/仓库:v1.0.0` | 可以从目标仓库拉取，系统为 Linux、架构为 amd64，配置摘要对应验收记录中的镜像身份 |
| `命名空间/仓库:latest` | 本次成功发布后与版本标签指向同一镜像；是可变标签，省略镜像标签时使用它 |
| `vpngate-source-v1.0.0.tar.gz` | 公开可下载，包含对应项目构建源码、精确锁定依赖原包、系统包来源与配方及原文声明 |
| `SHA256SUMS` | 可核验源码归档，不能以文件名代替摘要 |
| `validation.json` | 记录镜像身份、程序摘要和验收范围；当前每版本短试不表示重新完成三十分钟容量试验 |

镜像配置摘要、仓库清单摘要和程序摘要是不同对象，记录时分别命名，不直接互相比等。目标镜像拉取后的 `docker image inspect` 身份可与验收记录的 `image_id` 核对；源码归档按附件摘要核对。完整来源须持续可获得，临时内部构建附件不能代替本契约中的公开版本附件。

## 权限与失败恢复

仓库默认内容权限只读；发布任务为上传附件取得内容写权限。检出不保留令牌，GitHub 令牌只传给发布步骤，Docker Hub 密钥仅用于配置检查及登录。使用固定动作提交和固定构建工具链，保留默认 seccomp，验收必须使用项目专用 AppArmor 策略，不能以关闭防护绕过门槛。

同标签发布不互相取消；不同版本各自独立。已存在的版本附件不自动覆盖，已公开标签不移动，不用不同代码覆盖已发布版本。失败后先核对源码附件及镜像实际状态，修复用新版本。首次配置及真实发布由维护者触发，本次文档补齐不执行任何公开发布操作。
